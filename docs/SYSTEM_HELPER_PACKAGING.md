# StudioCast system-helper packaging

## Security boundary and prerequisite

The StudioCast installer AppImage is an unprivileged application payload. It
cannot safely bootstrap, elevate, or replace its own privileged authority. Host
package changes and v4l2loopback module/persistence changes require the separate
`studiocast-system-helper` OS package to already be installed through a signed
apt repository, a distribution repository, or an explicit administrator-
verified signed package.

The package installs exactly:

| Path | Owner | Mode |
| --- | --- | --- |
| `/usr/libexec/studiocast/studiocast-system-helper` | `root:root` | `0755` |
| `/usr/share/polkit-1/actions/com.studiocast.Installer1.policy` | `root:root` | `0644` |

The AppImage must only perform a read-only preflight of the fixed helper path,
type, owner, mode, version, protocol, and polkit availability. It must never run
a helper from an AppImage mount, source/archive/build directory, cache, XDG
directory, manifest path, environment override, or current working directory.
There is no `sudo`, `sudo -S`, `SUDO_ASKPASS`, or broad `pkexec` fallback.

If the package is missing or untrusted, Recommended stops before application
replacement whenever virtual-camera reconciliation is needed. Custom may
continue without a virtual camera only after that integration is explicitly
deselected and its degraded result acknowledged.

## Building the package payload

`packaging/system-helper/build_deb.sh` creates an unsigned Debian package using
only local repository files. It requires `dpkg-deb`, performs no network access,
and needs no root privileges:

```bash
packaging/system-helper/build_deb.sh /tmp/studiocast-system-helper-output
```

The script uses `dpkg-deb --root-owner-group`, so archive metadata assigns the
two installed files to `root:root`. The declarative copy/permission contract is
also recorded in `packaging/system-helper/package-layout.json` for release and
test verification.

Release infrastructure must sign the resulting repository metadata/package and
publish it through the supported stable channel. The repository intentionally
contains no signing private key. Building a local unsigned payload is not an
authorization or installation step.

## Authorization and protocol

Polkit authorizes only the fixed root-owned executable. StudioCast never sees or
transports the user's password. The client maps authorization outcomes to the
stable reason codes `authorization_granted`, `authorization_unavailable`,
`authorization_denied`, `authorization_cancelled`, and
`authorization_timeout`.

The authorized client invocation is exactly
`/usr/libexec/studiocast/studiocast-system-helper --json-stdin`. Polkit binds
authorization to the fixed executable path; the helper itself rejects every
other argument vector. This executable-plus-argument contract is recorded in
`package-layout.json` because polkit's executable annotation does not constrain
arguments.

The packaged Python entrypoint uses interpreter isolated mode (`-I`) so caller
`PYTHONPATH`, user-site packages, and other Python environment settings cannot
affect imports before the helper validates and sanitizes the request.

The helper reads one bounded UTF-8 JSON request on standard input and returns
one structured JSON result. It validates the complete request before the first
operation. The frozen v1 allowlist consists of:

- `packages.ensure.v1` for exact compiled package names on Ubuntu bases 22.04
  and 24.04;
- `v4l.module.load.v1` and `v4l.module.reload.v1` with a compiled module name,
  fixed absolute `modprobe` arrays, strict labels/device ranges, and live
  conflict/busy checks;
- `v4l.persistence.write.v1` and `v4l.persistence.remove.v1` for exactly the
  two namespaced StudioCast files.

All other operations and every unknown field are rejected. The helper accepts
no command, executable, argument vector, shell, script/source/archive/build
path, destination, working directory, environment, URL, download, arbitrary
content, module name, or package-manager flags. It invokes no shell and inherits
no caller path or language/plugin environment.

The two persistence files are generated by the helper, written atomically with
nofollow checks, and returned with SHA-256 hashes for manifest v2. Removal
requires the expected hashes and validates type, root ownership, marker, and
hash before unlinking. The legacy non-namespaced
`/etc/modules-load.d/v4l2loopback.conf` is never modified by this helper.

## Release checks

Before publishing the signed package:

1. Run `python3 tests/privileged_helper_tests.py` and Python compilation.
2. Build the local `.deb` and inspect it with `dpkg-deb --contents` and
   `dpkg-deb --info`; do not install it on the development host.
3. Confirm the two paths and modes match `package-layout.json` and that the
   package contains no AppImage/source/build payload.
4. Sign and publish through the supported package channel outside this
   repository; never add the private signing key to source control.
